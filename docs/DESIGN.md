# AgentGuard: design

## 1. Problem and principle

An AI agent with access to company tools can be tricked by a malicious prompt or by text hidden inside a document. If the only thing that stops it is the model "behaving", it is not stopped.

**Principle: never trust the model.** Every tool call passes through a gateway that enforces the human user's permissions in code. A fooled agent can never do more than its user is allowed to do. Detecting malicious text is an extra layer, never the main defence.

## 2. Architecture

```
 ┌──────────────┐  MCP (Streamable HTTP)   ┌──────────────────────────────────────┐   MCP    ┌──────────────────┐
 │  Demo agent  │  + user JWT on each call │            AgentGuard gateway        │ ───────► │  Finance tools  │
 │ (Spring AI,  │ ───────────────────────► │  MCP server side ──► pipeline ──►    │ service  │  (MCP server)    │
 │ Ollama/API)  │ ◄─────────────────────── │  MCP client side                     │  token   │                  │
 └──────────────┘   result or decision     │  policy · masking · approval · audit │ ◄─────── └────────┬─────────┘
                                           └───────┬──────────────────┬───────────┘                    │ JDBC
 ┌──────────────┐  REST + WebSocket (STOMP)        │ JDBC             │                               │
 │  Dashboard   │ ◄────────────────────────────────┘                  ▼                               ▼
 │ React, Vite  │                                ┌───────────────────────────────────────────────────────────┐
 └──────────────┘                                │ Oracle Database Free 23ai (one container, PDB FREEPDB1)   │
                                                 │  schema AGENTGUARD (policies, approvals, audit, limits)   │
                                                 │  schema FINANCE   (synthetic suppliers, employee, appts)     │
                                                 └───────────────────────────────────────────────────────────┘
```

Four Maven modules in one repository: `gateway`, `finance-tools`, `demo-agent`, plus `dashboard` (React). One `docker compose up` starts everything.

Two separate Oracle schemas with two separate database users: the gateway user cannot read finance tables, and the finance user cannot touch the audit log. Even a bug in one service cannot reach the other's data.

## 4. Data model (schema AGENTGUARD)

| Table | Main columns | Notes |
|---|---|---|
| `APP_USER` | id, username, password_hash, role, department | demo users. Roles: FINANCE_MANAGER, ACCOUNTANT, CLERK, HR, ADMIN |
| `POLICY_RULE` | id, priority, name, role, tool, condition_json, decision, mask_profile, reason, enabled | loaded from `policies.yml` at startup, shown read-only in the dashboard |
| `APPROVAL_REQUEST` | id, user_id, tool, args_json, action_hash, status, created_at, expires_at, decided_by, decided_at, used_at | status PENDING, APPROVED, REFUSED, EXPIRED, EXECUTED |
| `AUDIT_EVENT` | seq (identity), ts, user_id, role, tool, args_masked_json, decision, rule_id, reason, latency_ms, flags, prev_hash, hash | insert-only; the app user has no UPDATE or DELETE grant |
| `USAGE_COUNTER` | user_id, tool, window_start, count | daily export budget (per-minute limits live in memory) |

Schema FINANCE (all synthetic, generated by a seed script, never real data): `DEPARTMENT`, `EMPLOYEE` (with salary), `SUPPLIER` (tax_id, phone, address, iban, department_id, manager_id), `INVOICE`, `DOCUMENT` (free text, used for the prompt-injection demo).

## 5. One tool call, step by step

An agent acting for accountant Salma calls `get_supplier_record {supplierId: 42}`.

1. **Transport.** The agent's MCP request arrives at the gateway's MCP server endpoint with `Authorization: Bearer <user JWT>`.
2. **Identity.** Spring Security validates the signature and expiry. The claims become a `UserIdentity(userId, role=ACCOUNTANT, dept=ACCT)`. A missing, expired or forged token is refused here, before any tool logic runs.
3. **Context.** The gateway builds an immutable `ToolCallContext(identity, toolName, arguments, requestId, time)`.
4. **Rate limit.** A token bucket per (user, tool). If it's empty, the call is refused with DENY "rate limit".
5. **Argument validation.** The arguments are checked against the tool's strict schema: types, ranges, enums, maximum lengths. Unknown arguments are refused, so an agent cannot pass `_scope` or `department`.
6. **SQL guard** (only for tools that take a query). JSqlParser must find exactly one `SELECT`, on allowed tables and columns only, with no comments and no system views (`SYS.*`, `ALL_*`, `DBA_*`, `V$*`). The gateway then adds `FETCH FIRST n ROWS ONLY`.
7. **Policy engine.** Ordered rules, first match wins, DENY if nothing matches. The result is a `Decision(type, ruleId, reason, maskProfile)`.
8. **Branch on the decision.** DENY: return the reason. REQUIRE_APPROVAL: store an `APPROVAL_REQUEST` and return "waiting for approval, id 17". ALLOW or MASK: continue.
9. **Row scope.** The gateway adds trusted scope arguments to the upstream call (`scopeDept=ACCT`, `scopeManager=…`). The finance tools put them in the SQL `WHERE` clause. Finance tools only accept calls signed with the gateway's service token, and the agent can never set these fields (step 5).
10. **Upstream call** through the gateway's MCP client.
11. **Field masking.** The mask profile for the role is applied to the JSON result. A accountant gets `taxId: "****1234"`, and `iban` is removed. The model never receives what the user may not see.
12. **Untrusted content.** The result is wrapped as `{"untrusted": true, "content": …}` and scanned with simple rules ("ignore previous", "export all", tool names inside the text, …). A suspicious result is flagged, or quarantined if the policy says so.
13. **Audit.** One `AUDIT_EVENT` is written on every exit path, including refusals at steps 2 to 8. It's published to the dashboard over WebSocket.

## 6. Policy format

`policies.yml`, loaded into `POLICY_RULE` at startup. Rules are evaluated by ascending priority.

```yaml
- id: accountant-no-salaries
  priority: 10
  roles: [ACCOUNTANT, CLERK, FINANCE_MANAGER]
  tools: [get_employee_salaries]
  decision: DENY
  reason: "Salary data is restricted to HR."

- id: accountant-supplier-record-own-dept
  priority: 20
  roles: [ACCOUNTANT]
  tools: [get_supplier_record, search_suppliers]
  scope: SAME_DEPARTMENT          # becomes a WHERE condition upstream
  decision: MASK
  maskProfile: accountant-supplier     # hides taxId, address, iban
  reason: "Accountants see suppliers of their own department, without identity fields."

- id: bulk-changes-need-approval
  priority: 30
  roles: [CLERK, FINANCE_MANAGER, ADMIN]
  tools: [update_invoice, export_report]
  when: { "affectedRows": { "gt": 1 } }
  decision: REQUIRE_APPROVAL
  approvers: [ADMIN]
  timeout: PT5M
  reason: "Bulk changes and exports need a human approval."
```

**Design patterns.** The pipeline (steps 4 to 13) is a **Chain of Responsibility**: each step is a `GatewayFilter` class with one job, and the chain can stop early. Conditions inside a rule use the **Specification** pattern: small objects such as `RoleIs` and `ArgumentGreaterThan` that combine with and/or. The rejected alternative was one big service with nested `if` statements. That's harder to test and easy to break when a rule is added.

## 7. Approvals

The approval stores the **exact** call: tool, canonical arguments, and the user. `action_hash = SHA-256(user + tool + canonical args)`. When an approver accepts, the gateway itself executes the stored call once and marks it EXECUTED. The agent never re-sends it, so an approval cannot be reused for a different action, and an approval for user A can't be used by user B. A pending job marks PENDING requests older than `expires_at` as EXPIRED, and expired means refused. The agent can poll with a `get_approval_status` tool exposed by the gateway.

## 8. Tamper-evident audit

`hash = SHA-256(prev_hash || canonical_json(record))`. The first record uses a fixed genesis value. `verify-audit` (a CLI command and an admin endpoint) walks the chain in `seq` order and reports the first broken link. Inserts go through one transaction that locks the chain tail (`SELECT … FOR UPDATE` on a one-row `AUDIT_HEAD` table), so two parallel inserts cannot fork the chain.

Oracle 23ai also has native **blockchain tables**, which do this inside the database. We build our own chain so it's explainable and portable, and `DECISIONS.md` compares the two.

## 9. Threat model (short; the full version comes in `THREAT_MODEL.md`, Phase 10)

**We protect:** supplier identity and bank details, employee salaries, and the integrity of invoices and the audit trail.

**Attackers we consider:**
1. A user trying to exceed their role through the agent.
2. A prompt injection inside a document or tool result.
3. An agent sending tampered or oversized arguments.
4. Someone reusing or forging an approval.
5. An insider editing the audit log after the fact. We detect this; we don't prevent it.

**Out of scope:**
- A compromised gateway host or database administrator.
- Stolen user credentials (we only bind calls to them).
- Model jailbreaks that don't lead to a tool call. They're harmless here by design.
- Denial of service beyond simple rate limits.
- Secrets management beyond environment variables.

**Honest limit:** the injection scanner uses simple rules and will miss clever attacks. That's acceptable only because steps 2 to 9 don't depend on it.
